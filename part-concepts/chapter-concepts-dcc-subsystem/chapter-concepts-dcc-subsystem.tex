\unnumberedChapter{The DCC Subsystem}

The LCS runtime library builds the software foundation for implementing the layout control software. So far we have discussed the general operation, node and port functions, and callbacks. We are able to access node and port attributes as well as the firmware written for them. One part that was only touched upon briefly so far is the digital command control \texttt{(DCC)} subsystem. A significant part of the LCS messages deals with the control of running-equipment decoders, stationary decoders, and the track itself.

LCS messages for DCC commands are broadcast from controlling devices. For example, a handheld broadcasts a DCC command to set the speed. In a layout, there is one base station node that is responsible for producing the DCC signals for the track. The DCC signals are part of the physical LCS bus. While a base station design could directly supply the signal current to the track, larger layouts will typically have one or more boosters. They take the DCC signal from the LCS bus lines and generate the DCC signal current for their track section. All LCS messages for DCC operations are broadcast messages: all nodes can send them and all nodes can receive them. Handhelds, base stations, and boosters are thus just nodes on the LCS bus. Only the base station, however, generates the DCC signal.

The DCC standard defines mobile and stationary decoders. The DCC signal could also be used to control, for example, a set of turnouts via a stationary decoder. The LCS DCC message set contains messages for addressing a stationary decoder. Since the commands for stationary equipment are just DCC commands, they will be transmitted via the track as well and take away bandwidth on the track. A layout will therefore more likely use the LCS bus for managing stationary equipment. Besides, the producer/consumer model allows for much greater flexibility when building larger and partially automated layouts.

This chapter dives a little deeper into the DCC subsystem. At the heart of this subsystem is the base station node, which is in charge of managing locomotives and tracks. It receives LCS messages from devices such as a cab throttle and translates these commands into a series of DCC packets. The packets are the basis for the DCC track-power modules to produce the electrical signals on the track. The power module is either part of the base station or a separate booster. Base stations, boosters, and throttles are just nodes making use of the DCC commands in the LCS message set. They too can react to events and send events themselves. First we will look at a base station and what it takes to manage a locomotive session and to generate DCC packets for mobile and stationary decoders. Next, we will look at how a DCC packet actually gets out on the track.

\unnumberedSection{Locomotive Session Management}

Digital locomotives are equipped with a mobile decoder. The decoder analyzes the DCC packets on the track and, if addressed, performs the desired function. For each active locomotive, the base station first establishes a locomotive session. Across the layout, a locomotive is uniquely identified by its \textbf{cabId}. In DCC terms, this is the address of the locomotive. The DCC standard defines an address range that all decoders, mobile and stationary, share. Once a session is established for the cabId, the base station accepts LCS DCC commands, such as setting the speed, direction, or a function, and produces the corresponding DCC packet. We will see later what happens to the packet.

A base station typically works with two DCC tracks. There is the \textbf{main track}, which consists of all the track sections of the layout. Commands such as setting a locomotive speed and direction refer to this track. In addition, there is a \textbf{service track}, which is used to configure an individual locomotive. This track is electrically separated from the main track. However, when it comes to packet transmission, the two tracks are very similar. For base-station functionality, there are thus two key functional components. The first is locomotive session management; the second is the programming of a locomotive mobile decoder. The programming-track commands do not need a cabId, i.e. an address, as there should only be one locomotive on this track. This has to do with the way a decoder replies to the base station and will be discussed when we talk about decoder programming.

\unnumberedSection{Stationary Decoders}

While mobile decoders can be found in a locomotive, a stationary decoder can be found somewhere on the layout, for example close to a set of turnouts. It is connected to the main track and, just like its mobile cousin, decodes the DCC packets. Stationary decoders, called accessories in the NMRA standard, are assigned part of the address range and react to their configured address. The base station accepts LCS commands for such a decoder and generates the DCC packets for it.

As said before, the trend is to use a layout control system with a dedicated bus for the layout components. The key idea is to offload the track, where the engines run, from packets for the accessories. Another approach is to have a dedicated wire to all accessory decoders and send the DCC packets on this---in a sense, another track without locomotives. Our layout control system will support generating stationary-decoder packets and sending them via the main track. But the feature is implemented only for completeness. Maybe there is still one old decoder that can be put to use this way. Our layout will be controlled by the LCS bus.

\unnumberedSection{DCC Packet Generation}

The key task of locomotive session management is to generate the DCC packets for running and configuring mobile and stationary decoders. There are also packets, such as RESET or IDLE, that concern all decoders on the track. The DCC packets are described officially in the NMRA specifications. The \textbf{RailCommunity} specification documents (RCN-xxx) also have an excellent description of the packet layout and its interpretation. Each bit is either a zero or a one. A one bit has a period of at least 100 microseconds; a zero bit has a period of 200 microseconds. The exact timings are listed in the DCC standard; for now, this is a good enough description. The appendix contains links to their web pages for diving into all the details of the DCC packet format and protocol.

The base-station part that produces DCC packets is not concerned with how these packets are actually transmitted to the locomotive. This is the task of the DCC track-management component, which will be presented shortly. In general, a DCC packet is a stream of bits consisting of the preamble, a decoder address, and command bytes followed by a checksum byte. The preamble synchronizes a decoder with the upcoming data stream. The address tells which decoder is addressed, and the command bytes tell what needs to be done. Finally, the checksum makes sure that there was no error in transmitting the packet. The following figure depicts a simple packet showing the DCC idle command. Byte 1 is the command, byte 2 is zero. The high-level LCS DCC commands are translated by the base station into the corresponding DCC packets. There are two modes of transmission. With the first mode, any incoming command is translated and sent out immediately with an optional repeat count. Consider a locomotive speed-stop command. This, of course, has top priority. The second mode of transmission is a one-time fixed sequence of DCC packets for a high-level LCS command, such as is used for programming a decoder.

When no command is pending, the base station loops through all active session entries and sends packets to refresh the previously sent commands. For example, after sending a speed/direction command, this command is repeated periodically until a new command is issued for this locomotive session. While looping through the session table, only part of the necessary refresh packets is generated to make sure that all engines get a fair share of the track bandwidth in time. The complete refresh of speed/direction and function keys is spread over a couple of loop iterations. The DCC standard makes recommendations about what data to send and how often. Time to discuss how the DCC packets actually get to the track.

\unnumberedSection{Sending a DCC Packet}

The DCC track-management software component does not store any DCC packets other than the active packet that is currently being transmitted and the pending next packet. If it is busy sending a packet and there is already a pending packet queued, the packet-loading routine in the locomotive-session-management component waits until the pending packet becomes the current packet; then the next packet is queued. There is one more scenario to address. Suppose there is no packet currently sent from locomotive management and thus no packet to send to the track. In this case, we cannot just stop sending packets, as the locomotives draw their track power from the track signal. DCC track-management signal generation then just "invents" a packet to send out. This is the DCC IDLE packet for the main track and the DCC RESET packet for the programming track.

\unnumberedSection{DCC Track Signal Generation}

The primary task of a DCC track-signal generator is to receive the DCC packets generated by the base station and produce the hardware signals for the packet bits on the track. The other task is to monitor power consumption and optional RailCom-channel communication. DCC signals are square-wave signals with a defined duty-cycle period. A duty cycle of 58 microseconds represents a "DCC one." A duty cycle of 116 microseconds represents a "DCC zero" bit. Choosing 116 instead of 100 microseconds is still within the standard and allows the signals to be derived nicely from a 29-microsecond base clock.

This signal is sent to the track by reversing the polarity of the two track rails with the respective timing. Typically, an H-bridge such as that found in motor drivers performs this task. If the H-bridge is enabled, sending a "DCC one" means setting the digital input signals for the H-bridge to enable the "+" direction, and then reversing the digital signals for the "-" direction. The H-bridge hardware essentially reverses the track polarity according to digital zeroes and ones. The DCC packet is broken down bit by bit, and the digital signal is produced. That's it: we have a nice signal on the track. How the base-station firmware performs digital-signal generation is discussed in more detail in the base-station chapter.

\unnumberedSection{Power Consumption Monitoring}

DCC track management is also responsible for continuously monitoring track-power consumption. Considering that boosters can emit several amps, a short circuit over a longer time will certainly damage track and running equipment. It is therefore paramount to monitor the actual current consumption very closely. Monitoring track-power consumption can be done by measuring the voltage drop over a shunt resistor in series with the H-bridge. The controller's analog input periodically reads the value and processes the incoming data. From a software perspective, there are a couple of ways to measure the voltage and process it. One way is to measure at defined spots in the bit stream.

During signal generation, track-power consumption is measured at defined spots in the bit stream. A zero bit in a packet is a good place. The hardware just needs to make sure that the measurement completes during the 116-microsecond half-cycle of the zero bit. But certainly, there are other ways of measuring. An implementation could, for example, just sample on a periodic basis. When the configured consumption limit is exceeded, the value is stored in a node variable, DCC track management broadcasts a power-overload event, and shuts down the track. After a configured time, a restart is attempted. If restarting fails several times, the track is powered down permanently and manual intervention is required.

In addition, care needs to be taken to report a power-consumption value that reflects consumption over a period of time. Most locomotive decoders use a PWM (pulse-width modulation) approach to drive the motor in the engine. Depending on when the current-consumption measurement takes place, a high value or a zero value is returned. This does not reflect the actual power consumption. Therefore, several sampled values need to be used to build the "root mean square" value that indicates the actual power consumption.

\unnumberedSection{Decoder Programming Support}

There it is: a new locomotive, unpacked and sitting on the programming track. At a minimum, it needs to be told what its locomotive address will be on our layout. This task is accomplished by writing values to the decoder CV variables. A short locomotive address, for example, is written to CV~1.

DCC is a broadcasting protocol. Just like a radio station, you can send but not receive. In order to communicate back, the decoder raises its power consumption by a specific value and for a specific time period to indicate an OK. DCC track management needs to be able to detect this power-consumption fluctuation on the programming track. The detection is very similar to the previously discussed power-consumption monitoring, except that it is done in two steps. Before accessing a CV variable, the current decoder power consumption is measured to establish a baseline. This baseline is then compared with the actual power consumption after the CV access. A fluctuation of the value and duration specified by the DCC standard is considered a positive answer.

Reading all CV variables from a sophisticated decoder can easily take several minutes this way. Furthermore, this communication will not work on the main track, as there are many locomotives running, making it impossible to detect the rise in power consumption of a single locomotive. There had to be a better way, and there is: RailCom.

\unnumberedSection{RailCom Support}

RailCom was invented to address the problem of effective back communication on the programming track and also on the main track. DCC track management needs to implement the basic mechanism for this kind of communication. As DCC is a broadcasting protocol, no other transmission is possible while it is broadcasting. The key idea of RailCom is to briefly turn off the DCC signal and use this moment of quiescence to transmit data back from the decoder. The period in which the DCC output is turned off is called the cutout period. In addition to generating the DCC zeroes and ones on the track, DCC track management also implements cutout support.

The following figure depicts the overall signal timing for RailCom support. All the details can be found in the NMRA and RailCommunity standard documents, including a hardware reference implementation for a RailCom decoder and detector. After the last bit of a packet and during the first bits of the DCC packet preamble, the track signal is turned off. The decoder can now send data to the track and a signal detector can receive that data. The signal is a simple serial signal with a baud rate of 250 kbit/s. The following figure shows the DCC signal stream with the cutout period.

The individual messages available in channels one and two are called datagrams. For channel one, a datagram is 12 bits, i.e. the six bits encoded in the two raw data bytes; for channel two there are, in total, 36 bits. Each datagram starts with a four-bit identifier followed by the payload. A decoder is required to transmit its address every time it is addressed on channel one. Decoders send data on channel two only if explicitly requested. Channel one is a bit more chaotic when more than one decoder transmits. There are options to tell the decoder to stop sending its ID after an initial couple of times.

Channel two is only used when the decoder is explicitly addressed via a POM or XPOM DCC packet. Still, the base station needs to ensure that multiple requests from different decoders are transmitted one at a time and that there is enough time for the addressed decoder to answer. Also, the decoder needs to be addressed at least twice to complete a data request via RailCom. The first DCC packet tells what to get; the second DCC packet gives the controller a chance to put the RailCom reply in the next cutout packet. Finally, the DCC-A \texttt{(RCN-218)} standard uses the RailCom infrastructure for automatic locomotive registration and fast access to information in the decoder. For this purpose, channels one and two are combined into 48 bits of payload data. More on these topics is in the base-station chapter.

\unnumberedSection{DCC Track Sections}

A base station typically has a powerful main track and a less powerful programming track. For smaller layouts with one base station, this is a common scenario. In fact, the DCC standard requires the programming track to limit the maximum current to 100~mA after initialization, to avoid decoder damage from misconfiguration when testing new hardware. Larger layouts, however, are normally divided into several sections, each of which is controlled by a DCC booster. This has the key benefit that a short circuit affects only one track section. A DCC booster can also be equipped with a RailCom detector to implement, for example, locomotive detection on a per-section basis.

To DCC track management in a base station, a booster managing a track section is largely transparent. All track management is concerned with is that the DCC signals are generated. A base station for a larger layout could just have two H-bridges with a low current rating. One would produce the DCC signal for the main track, the other for the programming track. The programming-track output is directly connected to the programming track. The main-track output of the base station, however, is just a signal line that is then fed via the LCS-bus data lines into the boosters. All track sections receive the same DCC signal. All boosters are required to be wired with the same track polarity.

Boosters measure power consumption continuously and, in the case of exceeding the limits, send an event in which the base station is interested. Boosters are just LCS nodes like anything else. Port variables and events are the mechanism of communication. The actual implementation of a booster with variables and events is described in the hardware-module chapter on boosters.

There is one more thing to take care of. If a layout consists of more than one track section, the boosters may not be closely synchronized with respect to polarity and signal-generation timing. Again, it is first of all very important that all boosters have a common polarity wiring. If not, short circuits caused by running equipment crossing from one section to the other are likely to happen. If RailCom is enabled, the cutout period turns off one section as well. If one booster section is in cutout mode and the adjacent booster is not yet, crossing rolling equipment could create an unsafe condition. To avoid this problem, boosters need not only be closely synchronized, they should also feature a kind of "security gap" period before starting the cutout period. In this period, the booster is put into disconnected mode. This topic is also discussed a bit more in the booster-hardware part.

\unnumberedSection{A Short Glimpse at Software Implementation}

The LCS DCC base station plays the key role in the DCC subsystem. In addition to managing locomotive sessions and generating the necessary DCC packets, it is also responsible for managing the two tracks MAIN and PROG. Built on top of the LCS library, the base station has two key software components, one for session management and one for track management. The session-management part is rather straightforward: a table of active locomotive sessions that is processed periodically. The track-management part is, by nature, very close to the hardware. Two interlinked state machines, one for track-signal generation and one for track-power management, build the core of track management. The actual implementation of the two key parts of the base-station module is described in more detail in the base-station chapter.

\unnumberedSection{Summary}

This chapter gave a high-level overview of the DCC subsystem. The base-station and booster firmware implement DCC decoder management and track-signal generation. Locomotive session management is concerned with managing the running equipment. The key concept is the session, which contains all data needed to control a locomotive on the track. DCC packets for all active locomotives are generated and sent to the track-management component and thereafter periodically refreshed. Programming a locomotive decoder sends a DCC packet sequence that the addressed decoder interprets. There are two tracks, the main track and the programming track. While they differ in what they are used for and in their hardware capacities, both have as their key function putting out the packets generated by the locomotive-session-management software.

DCC track management is responsible for track-signal generation and track-power management. It takes the DCC packets and sends them out bit by bit: first the preamble and optional cutout period, then each data byte of the packet. Track-power consumption is monitored for the main track and is also used to detect the decoder-acknowledgement power-consumption fluctuation on the programming track. Exceeding the configured power-consumption limits results in a shutdown of the signal followed by a number of restart attempts. The DCC signals produced by the base station are ready to be used and can directly be fed to a track. However, in larger layouts, there will be track sections with a DCC booster for each section. Base stations and boosters are, you guessed it, just nodes on the LCS bus.
